## 💡 Concept of the Day

### gRPC — call a function on another machine like it is local

REST over JSON is the default for public APIs, but inside a system of microservices it has costs: hand-written clients that drift from the server, JSON parsing on every call, and no built-in streaming. **gRPC** fixes that by treating service-to-service calls as remote procedure calls: you define the service once in a `.proto` file, and gRPC generates the client and server code for you.

A `.proto` file is the contract. It declares the service's methods and message shapes using Protocol Buffers, a compact binary format. From that single file, the compiler produces type-safe clients and servers in Go, Python, Java, Node.js, C++, and more — so a Go service and a Python service can talk without either side hand-writing HTTP code.

Three things worth remembering:

- **Four call patterns, built in.** Unary (one request, one response), server streaming, client streaming, and bidirectional streaming — all declared with the same `stream` keyword. Live feeds and chatty services need no extra plumbing.
- **HTTP/2 under the hood.** Multiplexed streams over a single connection, header compression, and binary frames make gRPC noticeably faster and lighter than JSON over HTTP/1.1 for high-frequency internal traffic.
- **Contracts, not conventions.** Because the schema is the source of truth, breaking changes are caught at compile time instead of at 2 AM in production. The trade-off: binary payloads are not human-readable, and browsers cannot speak gRPC directly, so public-facing APIs usually stay REST.

## 🛠️ Tool of the Day

### GitHub Actions — CI/CD built into your repository

**GitHub Actions** is GitHub's built-in automation platform: define a workflow in a YAML file under `.github/workflows/`, and GitHub runs it for you on every push, pull request, release, or on a schedule. No separate CI server to set up.

```yaml
# .github/workflows/ci.yml
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run tests
        run: npm test
```

Why it is worth trying:

- **Zero setup for most projects.** Pick a starter workflow from the Actions tab and you have tests running in minutes — GitHub provides the runners.
- **A huge marketplace of reusable actions.** Checkout, language setup, caching, deployment, and security scanning are all one `uses:` line away, written by the community.
- **It automates more than CI.** Scheduled jobs, auto-labelling issues, publishing releases, and even this daily log repo's reminders are all workflows.

How to try it: in any repo, go to the **Actions** tab, choose a starter workflow for your language, commit it, and watch the first run go green.
