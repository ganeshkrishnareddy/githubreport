## 💡 Concept of the Day

### Dependency Caching in CI — stop re-downloading the world on every build

Every CI run on a fresh runner starts from scratch: it downloads your
dependencies (npm packages, Maven artefacts, Gradle modules) before it can
build or test anything. For large projects, that download step can take
longer than the build itself — and it repeats on every push and PR.

Dependency caching stores those downloaded packages between runs. On the
first run, the CI system saves the dependency directory to a cache. On the
next run, it restores that cache instead of hitting the network, and only
downloads what actually changed.

The trick is the **cache key**. A good key includes a hash of your
lockfile (`package-lock.json`, `pom.xml`, `Gemfile.lock`):

- Dependencies unchanged → same key → cache hit, fast run.
- Dependencies changed → new key → cache miss, fresh download, new cache saved.
- A `restore-key` (a shorter prefix of the key) gives a partial fallback:
  an older cache is better than no cache at all.

Two common mistakes: caching `node_modules` directly (it can contain
OS-specific binaries, so prefer the package manager's cache directory), and
using a key with no lockfile hash (stale dependencies silently reused).

## 🛠️ Tool of the Day

### actions/cache — GitHub's cache action for workflows

`actions/cache` is GitHub's official action for saving and restoring
files between workflow runs. It is the building block behind the
one-line `cache:` options in setup actions like `setup-node` and
`setup-java` — use those first when they fit, and reach for
`actions/cache` when you need custom paths or keys.

How to try it (Node.js example):

```yaml
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-node-
- run: npm ci
```

Why it is useful: faster CI, less network traffic, and quicker feedback
on every pull request — especially for projects with large dependency
trees. Start with one workflow, measure the before/after run time, and
only then roll caching out everywhere.
