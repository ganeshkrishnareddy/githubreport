## 💡 Concept of the Day

### Vector Embeddings — how search understands meaning

Keyword search only matches words. It cannot tell that "how do I reset my password" and "I forgot my login credentials" mean almost the same thing. **Vector embeddings** fix that by turning meaning into math.

An embedding model (a neural network trained on huge amounts of text, images, or audio) converts each item into a **vector** — a long list of numbers, often hundreds or thousands of dimensions. Items with similar meanings end up as points close together in that space, while unrelated items land far apart. Similarity is then just geometry: measure the distance between two vectors (usually with cosine similarity or Euclidean distance) and you have a score for "how alike are these two things?"

That one idea powers a lot of modern software: semantic search that finds relevant documents even when they share no keywords with the query, recommendation systems ("users who liked this also liked..."), duplicate detection, and RAG — the retrieval step that feeds relevant context to an LLM before it answers.

Three things worth remembering:

- **Same model, both sides.** The documents you store and the queries you search with must be embedded by the same model, or the vectors live in different spaces and the distances are meaningless.
- **Embeddings are not understanding.** They capture statistical patterns from training data, including its biases. A high similarity score means "these looked alike in the training data", not "these are truly the same".
- **Approximate is fast enough.** Exact nearest-neighbour search over millions of vectors is slow, so production systems use approximate indexes (like HNSW) that trade a tiny bit of accuracy for a huge speed-up.

## 🛠️ Tool of the Day

### pgvector — vector search inside PostgreSQL

**pgvector** is an open-source PostgreSQL extension that adds vector similarity search to the database you probably already run. Enable it with one statement, store embeddings in a normal table column, and query them with SQL — no separate vector database to operate, back up, or keep in sync.

```sql
CREATE EXTENSION vector;

CREATE TABLE docs (
  id serial PRIMARY KEY,
  content text,
  embedding vector(1536)
);

-- find the 5 documents closest in meaning to a query vector
SELECT content FROM docs
ORDER BY embedding <=> '[0.12, -0.45, 0.78, ...]'
LIMIT 5;
```

Why it is worth trying:

- **One less service.** Embeddings live next to your rows, inside the same transactions and backups, and you filter results with plain SQL `WHERE` clauses.
- **Distance operators built in.** `<->` for Euclidean distance, `<=>` for cosine distance, and `<#>` for inner product — pick the metric your embedding model was designed for.
- **Scales when you need it.** Exact search works out of the box; HNSW and IVFFlat indexes add fast approximate search for larger collections. It runs on PostgreSQL 13 and later, including most managed Postgres services.

How to try it: spin up a local Postgres, run `CREATE EXTENSION vector;`, embed a few sentences with any embedding model, insert the vectors, and run the query above. A semantic search over your own notes is a great first project.
