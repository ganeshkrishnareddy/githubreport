# 📝 Daily Log — 9 October 2026

## 💡 Concept of the Day: Dependency Confusion — the supply-chain trap

**The one-line version:** Attackers publish malicious packages with the *same name* as your private/internal dependencies on public registries (npm, PyPI, RubyGems) — and your package manager installs theirs.

**How the attack works:**
- Teams often name internal packages after their org (`acme-logger`) but never reserve that name on the public registry.
- An attacker registers `acme-logger` publicly with a higher version number.
- Package managers default to the public registry when a name matches in both places, so a normal install quietly pulls the malicious copy — and it runs install scripts with your privileges.

**Why it is dangerous:** Unlike phishing, nothing looks wrong. No one clicked a bad link; the code arrived through the normal dependency pipeline. Malicious packages can exfiltrate credentials, tokens, and source code silently.

**Defenses that work:**
- Use a lockfile (`package-lock.json`, `pip freeze`, `uv.lock`) and hash-pin dependencies.
- Point scoped packages (`@acme/*`) at your private registry, and reserve internal package names on public registries.
- Audit dependencies on every build with a vulnerability scanner — that's today's tool.

## 🛠️ Tool of the Day: OSV-Scanner

- **What:** A free, open-source vulnerability scanner by Google (https://github.com/google/osv-scanner) that checks your project's dependencies against the OSV.dev database of known vulnerabilities.
- **Why it is useful:** It scans lockfiles across languages (npm, PyPI, Go, Rust, and more) in seconds, so a compromised or vulnerable package shows up *before* it ships. No subscription, no SaaS — it runs on your laptop or in CI.
- **Try it:** Install via your package manager (`brew install osv-scanner` on macOS, or grab a release binary from the repo), then run `osv-scanner --recursive .` at your project root. Add the same command as a CI step to fail builds on critical findings.
