## 💡 Concept of the Day

### Contract Testing — catch breaking API changes before they reach production

In a microservices world, services talk to each other through APIs — and when one team changes its API, another team's service can break silently. Unit tests won't catch it (they test one service in isolation), and full end-to-end integration tests are slow, flaky, and expensive to run on every change. **Contract testing** sits in between.

The idea is simple: the **consumer** (the service calling the API) and the **provider** (the service serving it) agree on a **contract** — the exact requests the consumer will send and the responses it expects. Each side is then tested against that contract *in isolation*: the consumer test proves it can work with a mock that honours the contract, and the provider test proves the real API still honours it. If the provider changes something a consumer relies on, the provider's contract test fails — before anything ships.

Three things worth remembering:

- **Consumer-driven contracts.** The contract is written from what consumers actually use, not from everything the API can do. Fields nobody consumes are free to change without breaking tests.
- **Fast and reliable.** No deployed environment, no network flakiness — each side runs its half of the test locally, in its own CI pipeline.
- **It complements, not replaces, other tests.** Contract tests check the shape of the conversation, not business logic. You still need unit tests for behaviour and a few end-to-end tests for the critical paths.

## 🛠️ Tool of the Day

### Pact — consumer-driven contract testing for HTTP and message integrations

**Pact** is the most widely used open-source contract testing tool. The consumer test defines interactions (a request plus the expected response) and Pact records them into a contract file; the provider then replays that file against its real API to verify it still holds.

```js
// consumer test with @pact-foundation/pact
provider.addInteraction({
  uponReceiving: 'a request for a user',
  withRequest: { method: 'GET', path: '/users/1' },
  willRespondWith: { status: 200, body: { id: 1, name: 'Ada' } },
});
// run the consumer code against the mock, then publish the contract
```

Why it is worth trying:

- **Works across languages.** Pact has implementations for JavaScript, Java, Python, Go, .NET, Ruby, and more, so mixed-language teams share one contract format.
- **A broker keeps everyone in sync.** The Pact Broker stores contracts, shows which provider versions pass which consumer contracts, and can block a deploy when a verification fails.
- **It also covers messages.** Beyond HTTP, Pact tests async message contracts for queues like Kafka and SQS.

How to try it: follow the 5-minute guide on the Pact docs — write one consumer test for an API you already call, generate the contract, and run the provider verification against your real service.
