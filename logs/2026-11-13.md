# 📝 Daily Log — 13 November 2026

## 💡 Concept of the Day

### CORS — why the browser blocks your cross-origin fetch

Your frontend at `app.example.com` calls an API at `api.other.com` and the browser blocks it with a CORS error — even though the API works fine in curl. That is the **same-origin policy** doing its job: by default, a web page may only read responses from its own origin (same scheme + host + port), so a malicious site cannot silently read data from your bank or your inbox using your logged-in session.

**CORS** (Cross-Origin Resource Sharing) is the opt-in escape hatch. The server tells the browser which origins may read its responses, using headers:

- The browser sends an `Origin: https://app.example.com` header with the request.
- The server answers with `Access-Control-Allow-Origin: https://app.example.com` (or `*` for public data), and the browser lets your JavaScript see the response. No matching header, no data.

Two flavours to know:

- **Simple requests** (GET/POST with plain headers) go straight through; the browser just checks the response header.
- **Preflighted requests** (PUT/DELETE, JSON bodies, custom headers like `Authorization`) first send an `OPTIONS` request asking "may I?" — the server answers with the allowed methods and headers, and only then does the browser send the real request.

Common fixes when you hit a CORS error: add the header on the **server** (never in the frontend — the browser ignores it there), list exact origins instead of `*` when the request carries cookies (credentials + `*` is rejected), and in local dev use your framework's dev-server proxy so the browser sees a same-origin call. Never "fix" it by launching the browser with security disabled.

## 🛠️ Tool of the Day

### curl — debug a CORS failure in seconds

When the browser hides the details, `curl` shows you exactly what the server sends. Replay a preflight request yourself:

```bash
curl -i -X OPTIONS https://api.example.com/data \
  -H "Origin: https://app.example.com" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: Content-Type, Authorization"
```

Why it is worth trying:

- **See the real headers.** `-i` prints the response headers, so you can check whether `Access-Control-Allow-Origin` is present and matches your origin.
- **Rule out the browser.** If `curl` gets the data but the browser does not, the problem is CORS headers, not the API. If `curl` fails too, the API itself is the problem.

How to try it: `curl` ships with macOS and most Linux distros; on Windows it is built into Windows 10 and later. Add `-v` for the full request/response trace when you need it.
