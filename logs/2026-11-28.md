## 💡 Concept of the Day

### Bloom Filters — answer "definitely not here" using almost no memory

Imagine you run a service that checks whether a username is already taken, a URL was already crawled, or a password appeared in a breach — against a list of billions of entries. Storing the whole list in memory is expensive, and hitting the database every time is slow. A **Bloom filter** solves this with a clever trade-off: it is a tiny, fixed-size bit array that can tell you an element is *definitely not* in the set, or only that it *might* be.

Here is how it works. To add an element, you run it through a few hash functions, and each hash points at a position in the bit array, which you set to 1. To check membership, you hash the element again and look at those same positions. If any bit is 0, the element was never added — a guaranteed "no". If all the bits are 1, the element *might* be in the set, because other elements could have set the same bits by coincidence. That possible wrong "yes" is called a **false positive**.

Three things worth remembering:

- **No false negatives, ever.** A Bloom filter never says "not here" for something that is there — which is why it is safe to use as a cheap first check before an expensive lookup.
- **Space is the whole point.** A filter holding a million entries at a 1% false-positive rate needs roughly 1 MB — far less than storing the entries themselves. The trade-off is tuned by the size of the bit array and the number of hash functions.
- **You cannot delete or list items.** Bits are shared between elements, so clearing one could corrupt others, and the filter never stored the elements in the first place. When deletions matter, use a Counting Bloom filter or a Cuckoo filter instead.

Real systems use them everywhere: databases like Cassandra and RocksDB check a Bloom filter before touching disk, browsers check one before warning about a malicious URL, and CDNs use them to avoid caching lookups that will miss.

## 🛠️ Tool of the Day

### ripgrep (rg) — search your codebase at the speed of thought

**ripgrep** is a line-oriented search tool that recursively searches your current directory for a pattern — like `grep`, but dramatically faster and smarter out of the box. It respects your `.gitignore` by default, so it skips `node_modules`, build output, and hidden files without you asking, and it searches in parallel across your CPU cores.

```bash
# Install (macOS / Debian-Ubuntu)
brew install ripgrep        # or: sudo apt install ripgrep

# Find every use of a function
rg "calculateTotal"

# Search only Python files, showing line numbers
rg --type py "TODO"

# Search and replace a preview (with --replace)
rg "oldName" --replace "newName"

# Search a specific folder, case-insensitive
rg -i "error" ./logs
```

Why it is worth trying:

- **Blazing fast.** On large repos it is often several times faster than `grep -r`, because of parallel search and smart skipping of ignored files.
- **Sane defaults.** Hidden files and `.gitignore`d paths are skipped automatically, and matches are colour-highlighted with line numbers.
- **Plays well with your editor.** It is the search engine behind VS Code's fast search and the default for many fuzzy finders, so learning its flags pays off everywhere.

How to try it: install it, then run `rg "TODO"` in any project you are working on — the speed difference from plain `grep` is immediately obvious.
