## 💡 Concept of the Day: Multi-Stage Docker Builds

**The one-line version:** A Dockerfile with multiple `FROM` stages lets you *build* in a fat image (compilers, SDKs, dev tools) and *ship* a slim one — only the final stage's files end up in the image you push.

**How it works:**
- Each `FROM` line starts a new build stage; you name stages with `AS builder`.
- `COPY --from=builder /app/server /usr/local/bin/server` copies just the built artifact into the final stage — the compiler, the source tree, and the dev dependencies never make it into the shipped image.
- Smaller images pull faster, start faster, and carry a smaller attack surface (no compiler or package manager left behind for an attacker to play with).

**Example:**
```dockerfile
FROM golang AS builder
WORKDIR /app
COPY . .
RUN go build -o server .

FROM alpine
COPY --from=builder /app/server /usr/local/bin/server
CMD ["server"]
```

**Why it matters:** Single-stage Dockerfiles that compile *and* run in the same image are the #1 reason teams ship gigabyte-sized images full of build tools. Multi-stage builds are the standard fix — and you can add a separate `test` stage too (`docker build --target test`), keeping CI checks out of production.

## 🛠️ Tool of the Day: dive

- **What:** dive is a terminal UI for exploring Docker image layers (https://github.com/wagoodman/dive) — it shows what each layer added, changed, or removed, and estimates how much wasted space your image carries.
- **Why it is useful:** Multi-stage builds only help if you actually check the result. dive shows exactly which layer smuggled in those surprise megabytes, and its efficiency score tells you whether your cleanup steps really worked.
- **Try it:** `dive <your-image-tag>` to explore, `dive build -t myapp .` to build-and-inspect in one shot, or `CI=true dive myapp` to fail CI when wasted space crosses your threshold.
