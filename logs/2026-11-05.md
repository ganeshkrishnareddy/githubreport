## 💡 Concept of the Day

### Caching Strategies — trade a little memory for a lot of speed

A cache is a fast, temporary store that sits in front of a slower source of truth, like a database or an upstream API. When the same data is requested again and again, serving it from the cache avoids repeating expensive work, which is why caching is one of the highest-impact performance wins in any system.

Three strategies cover most use cases:

- **Cache-aside (lazy loading).** Your app checks the cache first. On a hit, it returns the cached value. On a miss, it reads from the database, stores the result in the cache with a time-to-live (TTL), and returns it. Simple, and the cache only holds data that is actually requested.
- **Write-through.** Every write goes to the cache and the database together, so the cache is never stale. Reads are always fast, but every write pays the cost of updating both.
- **Write-behind (write-back).** Writes go to the cache first and reach the database later, in the background. Very fast writes, but a crash before the flush can lose data, so it suits data you can afford to lose or rebuild.

Whichever pattern you pick, two disciplines keep a cache correct:

- **Always set a TTL.** A TTL is your safety net: even if you forget to invalidate an entry, it expires on its own instead of serving stale data forever.
- **Invalidate on write.** When the underlying data changes, delete or update the affected cache keys. The hardest part of caching is not storing data, it is knowing when to throw it away.

## 🛠️ Tool of the Day

### Redis — the in-memory store behind most caches

Redis is an open-source, in-memory data structure store that is most commonly used as a cache. Because it keeps data in memory, reads and writes take microseconds rather than the milliseconds a disk-backed database needs.

```bash
# Store a value that expires after 15 minutes (900 seconds)
SET user:42 '{"name":"Asha"}' EX 900

# Read it back
GET user:42

# Drop it when the data changes
DEL user:42
```

That handful of commands covers the core cache-aside flow: `SET` with `EX` for the TTL, `GET` for the lookup, and `DEL` for invalidation. Redis also supports richer structures (lists, sets, sorted sets, hashes) when a plain key-value cache is not enough, plus eviction policies like `allkeys-lru` that automatically drop the least recently used keys when memory fills up.

Try it: run Redis locally with Docker (`docker run -p 6379:6379 redis`), cache the result of one slow query in your own project with a short TTL, and watch the second request return instantly. If Redis is ever unreachable, fall back to the database instead of failing the request: a cache should make things faster, never break them.
