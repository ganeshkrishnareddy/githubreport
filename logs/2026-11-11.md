## 💡 Concept of the Day

### Rate Limiting — put a speed limit on your API

Every API has a breaking point: too many requests at once and it slows down, crashes, or runs up a huge cloud bill. Rate limiting caps how often a client can repeat an action within a time window — for example, 100 requests per minute per user — and politely refuses the rest with HTTP status `429 Too Many Requests`.

Why it matters:

- **Stops abuse.** A brute-force login attack needs thousands of password guesses; limit logins to a few attempts per minute and the attack becomes useless.
- **Keeps the service up for everyone.** One misbehaving client or runaway script cannot hog all the capacity; everyone else keeps working.
- **Controls costs.** Every request burns compute, bandwidth, and database time — limits keep usage (and the bill) predictable.

Three common algorithms:

- **Fixed window.** Count requests in a set window (e.g. one minute); reset the counter when the window ends. Simple, but a burst can straddle two windows and slip through at double the rate.
- **Sliding window.** Like a fixed window, but the window moves with each request, smoothing out bursts.
- **Token bucket.** Tokens refill at a steady rate; each request spends one. Short bursts are allowed (spend saved tokens) while the long-term average stays capped — a good balance of fairness and flexibility.

Good habits: return the `429` status with a `Retry-After` header so clients know when to try again, limit by user or API key (not just IP, since many users can share one IP), and keep limits generous enough that normal users never notice them.

## 🛠️ Tool of the Day

### Redis — the in-memory store behind most rate limiters

Redis is an open-source, in-memory data store that keeps data in RAM instead of on disk, so reads and writes take microseconds. That speed makes it the go-to building block for rate limiting, caching, queues, and leaderboards.

Why it is worth trying:

- **Atomic counters with expiry.** One `INCR` on a key plus an expiry gives you a fixed-window counter — no race conditions, no extra database round trips.
- **More than a cache.** Sorted sets power leaderboards, streams power event logs, and pub/sub powers lightweight messaging — one tool, many jobs.
- **Easy to run locally.** A single Docker command starts a server you can experiment with in minutes.

How to try it:

```bash
docker run -p 6379:6379 redis   # start Redis locally
redis-cli ping                  # should reply PONG
redis-cli INCR ratelimit:user42 # count a request (returns 1, 2, 3, ...)
redis-cli EXPIRE ratelimit:user42 60  # reset the window after 60 seconds
```

Pair the counter with a check — if the count passes your limit, answer `429` — and you have a working rate limiter in a few lines of code.
