## 💡 Concept of the Day

### Rate Limiting — Token Bucket vs Leaky Bucket

Every public API has a limit: too many requests from one client and the server falls over, or a runaway script burns your budget. **Rate limiting** caps how often someone can repeat an action in a given window — and the two classic algorithms behind it work very differently.

**Token bucket** is the friendly one. Imagine a bucket that holds up to *N* tokens and refills at a steady rate. Each request spends one token; an empty bucket means the request is rejected (usually with HTTP `429 Too Many Requests`) until tokens refill. Because tokens accumulate while a client is idle, short bursts are allowed — exactly how real API usage behaves. Stripe, GitHub, and AWS all use this approach for their APIs.

**Leaky bucket** is the strict one. Requests queue up and drain out at a constant rate, like water leaking from a bucket. The output rate never spikes, no matter how bursty the input is. That makes it ideal when a fragile downstream (a database, a payment gateway) must never see a spike — but clients pay for the smoothness with extra latency while they wait in the queue.

Three things worth remembering:

- **Fixed window is the naive option.** A counter that resets every minute is simple, but a client can fire the full limit twice in milliseconds across a boundary reset. Sliding windows and token buckets close that gap.
- **Limit by the right key.** Per-IP limits stop floods; per-user or per-API-key limits stop abuse from one account without punishing everyone behind a shared NAT.
- **Always fail open when the limiter itself breaks.** If the Redis store behind your limiter goes down, letting traffic through is usually safer than blocking every user at once.

## 🛠️ Tool of the Day

### ripgrep (`rg`) — search code at ludicrous speed

**ripgrep** is a line-oriented search tool written in Rust that recursively searches your codebase for a regex pattern — like `grep -r`, but dramatically faster. It parallelizes across CPU cores, respects `.gitignore` by default (so it skips `node_modules`, `.git`, and build output), and skips hidden and binary files unless you ask otherwise.

Why it is useful: finding every use of a function, a TODO, or a hardcoded secret across a large repo takes milliseconds instead of seconds, and the sane defaults mean you rarely need extra flags. It is the search engine behind many editors and AI coding tools for exactly this reason.

Try it:

```bash
# Install (Debian/Ubuntu)
sudo apt install ripgrep

# Find a pattern, with line numbers, in Python files only
rg -n -tpy "TODO|FIXME"

# Case-insensitive search, showing 2 lines of context
rg -i -C 2 "rate_limit"
```
