## 💡 Concept of the Day

### Webhooks — let events come to you

Polling asks "anything new?" over and over. A webhook flips that around: when something happens, the source sends an HTTP POST to a URL you registered, with the event details in the body. A push to a repo, a successful payment, or a new form submission can trigger your code within seconds, without a single wasted request.

A webhook delivery has three parts worth knowing:

- **The event.** The sender names what happened, usually in a header (GitHub uses `X-GitHub-Event`) and an `action` field in the body, so one endpoint can handle many event types.
- **The payload.** The JSON body describing the event: which repo, who acted, what changed. Subscribe only to the events you actually handle, so your server is not flooded with noise.
- **The signature.** Anyone can POST to a public URL, so a webhook endpoint must prove the sender is genuine. The sender signs the raw request body with a shared secret (HMAC-SHA256 for GitHub, sent as `X-Hub-Signature-256`) and your server recomputes the signature and compares it in constant time. Never skip this check, and always hash the raw body: parsing JSON and re-serialising it changes the bytes and breaks the signature.

Three habits make webhooks reliable in production:

- **Respond fast, work later.** Acknowledge the delivery (HTTP 200) immediately and queue the real work. Slow handlers get timed out and redelivered, which means duplicate processing.
- **Be idempotent.** Deliveries can repeat, so use the delivery ID (GitHub's `X-GitHub-Delivery`) to ignore duplicates.
- **Expect failure.** Endpoints go down and networks drop packets, so log every delivery, return clear status codes, and design your handler to survive a retry.

## 🛠️ Tool of the Day

### ngrok — test webhooks on your laptop

Webhooks need a public HTTPS URL, but your code runs on localhost. [ngrok](https://ngrok.com/docs/share-localhost/webhooks) bridges that gap: it opens a secure tunnel from a public URL to your local server, so real webhook deliveries from GitHub, Stripe, or any other provider reach your machine while you develop.

```bash
# Start your app on port 3000, then in another terminal:
ngrok http 3000
```

Copy the forwarding URL it prints (something like `https://abc123.ngrok-free.app`) and paste it as the webhook URL in the provider's settings, with a path like `/webhooks/github`. The local inspector at `http://127.0.0.1:4040` shows every incoming request, headers and body included, and lets you replay a delivery while you debug.

Try it: point a test repo webhook at your ngrok URL, push a commit, and watch the delivery arrive in the inspector. Then break your signature check on purpose and confirm a forged request gets rejected.
