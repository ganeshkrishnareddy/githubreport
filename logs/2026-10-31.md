## 💡 Concept of the Day

### Feature Flags — ship code without releasing the feature

Deploying code and releasing a feature are two different moments, and feature flags are what separates them. A feature flag (also called a feature toggle) is a runtime switch in your code: when it is on, users see the new behaviour; when it is off, they get the old one. No redeploy is needed to flip it.

That separation buys three practical powers:

- **Gradual rollouts.** Turn a feature on for 1% of users, watch errors and metrics, then climb to 10%, 50%, 100%. A bad release hurts a slice of traffic, not everyone.
- **Kill switches.** If a feature misbehaves in production, an operator can switch it off from a dashboard in seconds, instead of waiting for a hotfix deploy.
- **Trunk-based development.** Unfinished work can merge to the main branch hidden behind a flag, so teams avoid long-lived feature branches and their painful merges.

Flags come in kinds, and each kind has a different lifespan. Release flags hide unfinished work and should live days to weeks. Experiment flags split traffic for A/B tests and die when the experiment ends. Ops flags control behaviour under load, and permission flags gate features by plan or user group and may live much longer.

The catch is flag debt. Every forgotten flag leaves two code paths to test and maintain, and a codebase full of stale flags gets harder to reason about. The discipline that keeps flags useful: give each flag an owner, set an expiry date when you create it, and remove the flag and its dead code path once the rollout is complete.

## 🛠️ Tool of the Day

### Unleash — open-source feature flag management

[Unleash](https://docs.getunleash.io/concepts/feature-flags) is an open-source platform for managing feature flags, self-hosted or in the cloud. Instead of scattering `if` checks on environment variables across services, you define flags in one dashboard with activation strategies: gradual percentage rollouts, targeting by user ID or segment, and per-environment settings for dev, staging, and production.

It ships SDKs for most major languages, so checking a flag is a single call in your code, and the SDKs cache values locally so flag checks stay fast even if the flag service is briefly unreachable.

Try it: run the self-hosted version with Docker, create a flag called `new-checkout`, enable it for 10% of users in staging, and wire one `if` branch in a small project to it. When you are done, practise the most important step: delete the flag and its old code path.
