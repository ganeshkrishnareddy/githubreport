## 💡 Concept of the Day

### Secrets Management — keep credentials out of your code

A secret is any credential your code needs but nobody should read: an API key, a database password, a private key, a token. The moment one lands in a git commit, it is compromised, because git history never forgets. Deleting the file later does not help: the secret still sits in an old commit, and bots scan public repos for fresh keys within minutes.

Good secrets management follows four rules:

- **Never hardcode.** Read secrets from environment variables or a secrets manager at runtime, never from source files, and never from a `.env` file that gets committed by accident.
- **Separate config from code.** The same build should run in development, staging, and production with different secrets injected per environment. If a secret changes, you redeploy config, not code.
- **Least privilege and rotation.** Every secret should do exactly one job, and be replaceable. Short-lived credentials beat long-lived ones: a leaked token that expires in an hour is a far smaller incident than one that works forever.
- **Assume a leak will happen.** When a secret is exposed, revoke and rotate it immediately, then clean the history. Reverting the commit is not enough; the key must be treated as public from the moment it was pushed.

This applies to personal projects too. A side project with a hardcoded cloud key is the classic way a weekend hobby turns into a surprise bill.

## 🛠️ Tool of the Day

### Gitleaks — catch leaked secrets before attackers do

[Gitleaks](https://github.com/gitleaks/gitleaks) is an open-source secret scanner for git repos. It walks your code and commit history looking for patterns that resemble credentials: API keys, tokens, private keys, and database passwords, using a large built-in ruleset plus entropy checks for high-randomness strings.

```bash
# Scan the whole history of the current repo
gitleaks detect

# Check only what you are about to commit
gitleaks protect --staged
```

Run `detect` when you inherit a repo, to learn whether anything was ever leaked. Run `protect --staged` as a pre-commit hook, so a secret never enters history in the first place. It also ships a GitHub Action, so the same check can gate every pull request in CI.

Try it: add `gitleaks protect --staged` to a test repo's pre-commit hook, stage a file containing a fake-looking API key, and watch the commit get blocked. Remember: a scanner catches known patterns, not every custom key format, so it complements good habits, it does not replace them.
