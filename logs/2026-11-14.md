## 💡 Concept of the Day

### DNS — how the internet finds your server

You type `github.com` and the page loads — but computers do not talk in names, they talk in IP addresses. **DNS (Domain Name System)** is the phone book that translates a human-readable name into an IP address your browser can connect to.

Here is what happens in the milliseconds after you press Enter:

1. **Your resolver asks around.** Your computer first checks its own cache, then asks a recursive resolver (usually run by your ISP or a public service).
2. **Root, then TLD, then authoritative.** The resolver asks a root server where `.com` lives, then the `.com` server where `github.com` lives, then the authoritative server for `github.com` itself, which returns the actual IP address.
3. **The answer gets cached.** Each record carries a TTL (time-to-live) — for that many seconds, the resolver reuses the answer instead of asking again.

A few record types worth knowing:

- **A / AAAA** — map a name to an IPv4 / IPv6 address.
- **CNAME** — an alias: one name points to another name (often used for subdomains).
- **MX** — tells mail servers where to deliver email for a domain.
- **TXT** — free-form text, used for verification and email security (SPF, DKIM, DMARC).

Two practical consequences: a DNS change is never instant — old cached answers linger until their TTL expires, so plan changes with a low TTL ahead of time. And DNS is a common attack surface: always enable DNSSEC where you can, and use a reputable resolver, because a poisoned answer can send your users to a fake site.

## 🛠️ Tool of the Day

### dig — ask DNS anything, from your terminal

When a domain does not resolve, do not guess — ask DNS directly. **dig** (domain information groper) queries name servers and shows you exactly what they answer, including the record, its TTL, and which server responded.

```bash
dig github.com            # A record: which IP does the name point to?
dig github.com MX         # where does mail for the domain go?
dig @8.8.8.8 github.com   # ask Google’s resolver instead of your default
dig +trace github.com     # follow the full chain: root → TLD → authoritative
```

Why it is worth trying:

- **Debug DNS changes.** After updating a record, `dig` shows whether the new value has propagated — and to which resolver.
- **Compare resolvers.** Query your ISP’s resolver and a public one side by side to spot stale caches.
- **Learn the protocol.** `+trace` turns an invisible lookup into a visible chain of servers.

How to try it: `dig` ships with BIND on macOS and most Linux distros (on Debian/Ubuntu: `sudo apt install dnsutils`). On Windows, `nslookup` covers the basics, or use WSL.
