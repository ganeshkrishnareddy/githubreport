# 📝 Daily Log — 10 October 2026

## 💡 Concept of the Day: RAG (Retrieval-Augmented Generation)

**The one-line version:** RAG lets an LLM answer questions from documents it was never trained on — by searching your data for the relevant passages and handing them to the model as context before it generates a reply.

**How it works:**
- **Chunk** your documents (docs, FAQs, PDFs) into short passages.
- **Embed** each chunk into a vector — a list of numbers that captures its meaning — using an embedding model, and store them in a vector index.
- **Retrieve:** embed the user's question the same way; the index returns the chunks whose vectors are closest to it.
- **Generate:** those chunks go into the prompt, and the LLM answers *from them*, citing the sources it used.

**Why it matters:** LLMs have two hard limits: knowledge frozen at training time, and zero access to your private data. RAG fixes both without retraining. Grounded answers hallucinate less, stay current (update the index, not the model), and are auditable because the model can point at the passages it read. The term comes from a 2020 paper by Lewis and colleagues at Facebook AI Research that paired a pre-trained language model with a dense vector index.

## 🛠️ Tool of the Day: pgvector

- **What:** An open-source Postgres extension for vector similarity search (https://github.com/pgvector/pgvector). You store embeddings in a `vector` column right next to your relational data — no separate vector database to run.
- **Why it is useful:** You keep Postgres's ACID transactions, JOINs, and backups, and add nearest-neighbor search with HNSW and IVFFlat indexes plus cosine, L2, and inner-product distances. It is the fastest way to add RAG retrieval to a project that already runs Postgres.
- **Try it:** spin it up in Docker and run a similarity query:
```sql
CREATE EXTENSION vector;
CREATE TABLE docs (id SERIAL PRIMARY KEY, content TEXT, embedding vector(384));
SELECT content FROM docs ORDER BY embedding <=> '[0.1, 0.2, ...]' LIMIT 5;
```
