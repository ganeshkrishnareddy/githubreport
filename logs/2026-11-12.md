## 💡 Concept of the Day

### Load Balancing — spread the traffic, stay up

One server can only handle so much. When traffic grows, a single machine becomes a bottleneck — and a single point of failure. A **load balancer** sits in front of a pool of servers and spreads incoming requests across them:

- **No single point of failure.** If one server crashes, the balancer stops sending it traffic and the rest keep serving users.
- **Scales horizontally.** Add more servers to the pool instead of buying one bigger machine.

Three common ways to pick a server:

- **Round robin.** Requests go to each server in turn — simple and fair when all servers are equal and requests cost roughly the same.
- **Least connections.** Send the next request to the server with the fewest active connections — better when some requests are slow (file uploads, reports) and others are quick.
- **IP hash.** Hash the client's IP so the same client always lands on the same server — useful when the app keeps session state on the server.

Good habits: health-check your backends so dead servers leave the rotation automatically, keep servers stateless where possible, and make the balancer itself redundant so it doesn't become the new single point of failure.

## 🛠️ Tool of the Day

### NGINX — the reverse proxy that doubles as a load balancer

NGINX is a fast, open-source web server and one of the most popular software load balancers. A few lines of config turn it into a traffic distributor:

```nginx
http {
    upstream myapp {
        least_conn;
        server app1.example.com;
        server app2.example.com;
        server app3.example.com;
    }

    server {
        listen 80;

        location / {
            proxy_pass http://myapp;
        }
    }
}
```

Why it is worth trying:

- **Batteries included.** Round robin is the default — just list your servers in an `upstream` block and `proxy_pass` to it. Switch to `least_conn` or `ip_hash` with one line.
- **Passive health checks.** With `max_fails` and `fail_timeout`, NGINX stops sending traffic to a repeatedly failing server.

How to try it:

```bash
docker run -p 80:80 nginx   # start NGINX locally
nginx -t                    # test your config before reloading
nginx -s reload             # apply a new config without dropping connections
```

Run two tiny backends on different ports, point an `upstream` block at both, and watch requests alternate between them.
