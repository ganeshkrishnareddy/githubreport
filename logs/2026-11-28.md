## 💡 Concept of the Day

### Connection Pooling — stop paying the handshake tax on every request

Every time your app talks to a database, opening a fresh connection is expensive: a TCP handshake, a TLS handshake if enabled, authentication, and session setup — often tens of milliseconds before a single query runs. Under load, that overhead piles up, and databases also cap how many simultaneous connections they accept. **Connection pooling** fixes this by keeping a small set of already-open connections ready to reuse.

A pool sits between your app and the database. When a request needs the database, it borrows a connection from the pool, runs its queries, and returns the connection when done. The next request reuses that same warm connection instead of opening a new one — no handshake, no login, just the query.

Three things worth remembering:

- **Size the pool to your workload, not your traffic.** A common starting rule is a small pool (roughly one connection per CPU core on the database, plus a few spare) — too many connections make the database slower, not faster, because it spends its time switching between them.
- **Borrow short, return fast.** Holding a pooled connection while you call another API or wait on user input starves other requests. Get the connection, run the query, give it back.
- **Pools exist at every layer.** Your framework or driver usually has a built-in pool (like HikariCP for Java or `pg.Pool` for Node), while dedicated poolers such as PgBouncer sit in front of PostgreSQL and let hundreds of app servers share a handful of real database connections.

Connection pooling will not fix a slow query — but if your app opens a new connection per request, pooling is often the single biggest latency win you can get for free.

## 🛠️ Tool of the Day

### jq — `sed` for JSON data

**jq** is a lightweight command-line tool for slicing, filtering, and transforming JSON — the same way `grep` and `sed` work on plain text. APIs, logs, and config files are mostly JSON now, and jq lets you pull exactly the field you need without writing a throwaway script.

```bash
# Install (macOS / Debian-Ubuntu)
brew install jq            # or: sudo apt install jq

# Pretty-print a JSON file
jq . response.json

# Pick one field out of an API response
curl -s https://api.github.com/repos/jqlang/jq | jq .stargazers_count

# Filter an array: names of all open issues
jq '.[] | select(.state == "open") | .title' issues.json

# Reshape data: build a new object from existing fields
jq '{name: .login, repos: .public_repos}' user.json

# Raw output, no quotes — handy in shell scripts
jq -r '.tag_name' release.json
```

Why it is worth trying:

- **Zero setup.** A single static binary with no runtime dependencies — it works the same on your laptop and on a remote server.
- **Pipes compose beautifully.** Chain `curl | jq` to inspect any API, or `jq` inside shell scripts to turn JSON into variables and decisions.
- **Filters are a real language.** Beyond picking fields, jq can map, group, sort, and aggregate — whole data transformations in one line.

How to try it: next time an API returns a wall of JSON, pipe it through `jq .` first, then drill in with `jq .someField` — you will stop reaching for Python one-liners.
