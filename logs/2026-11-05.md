## 💡 Concept of the Day

### Webhooks — let services call you back

Polling asks "anything new?" over and over. A webhook flips that around: you register a URL with a service, and the service sends your server an HTTP POST the moment an event happens, like a payment succeeding, a pull request opening, or a message arriving. No wasted requests, no waiting for the next poll cycle.

A webhook delivery has three parts:

- **The event** — what happened, e.g. `payment.succeeded` or `pull_request.opened`, usually as a JSON body.
- **The headers** — metadata such as a unique delivery ID, a timestamp, and a signature proving the sender is who it claims to be.
- **Your endpoint** — an ordinary route on your server that receives the POST and acts on it.

Three rules make a webhook receiver production-ready:

- **Verify the signature.** Your endpoint is a public POST URL, so anyone can send it fake events. Providers sign the raw request body with a shared secret (usually HMAC-SHA256); recompute that signature on your side and compare it in constant time before trusting anything.
- **Acknowledge fast, process slowly.** Reply with a 2xx status quickly, then do the heavy work in a background job. A slow handler looks like a failure to the provider, which then retries and may deliver the same event twice.
- **Handle duplicates.** Because retries happen, design your handler to be idempotent: use the delivery ID to skip an event you have already processed.

## 🛠️ Tool of the Day

### ngrok — test webhooks on your own machine

Webhooks need a public HTTPS URL, but during development your app runs on localhost, which no provider can reach. [ngrok](https://ngrok.com/docs/share-localhost/webhooks) solves this by opening a secure tunnel from a public URL to your local server.

```bash
# Start your app, then expose it (example: port 3000)
ngrok http 3000
```

ngrok prints a public forwarding URL. Paste that URL into the provider's webhook settings, and real events start arriving at your laptop. Its built-in traffic inspector lets you see every request's headers and body, and replay a past request with one click instead of triggering the event again from scratch.

Try it: run a tiny server with a `/webhooks/test` route that logs the request body, expose it with `ngrok http 3000`, and send it a test event from a provider's dashboard or a tool like webhook.site. Remember to verify signatures in real integrations, and never expose a tunnel to anything sensitive without access controls.
