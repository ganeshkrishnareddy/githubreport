## 💡 Concept of the Day

### Rate Limiting — the token bucket that keeps APIs alive

Every public API caps how fast you can call it. That cap is **rate limiting**: a budget of requests per client, per window of time, enforced so one heavy user (or one bug in a loop) cannot take the whole service down for everyone else. When you exceed it, the API answers `429 Too Many Requests` and tells you, via a `Retry-After` header, when to try again.

The most widely used algorithm behind those limits is the **token bucket**. Picture a bucket that holds up to *N* tokens and refills at a steady rate, say 10 tokens per second. Every request costs one token. If the bucket has a token, the request goes through; if it is empty, the request is rejected. Because tokens accumulate while you are idle (up to the bucket's capacity), you can spend them in a short burst — which is exactly how real clients behave: quiet, then a flurry of calls when a page loads.

Three things worth remembering:

- **Two numbers define the policy.** Refill rate = the sustained speed allowed; bucket capacity = how big a burst is tolerated. Stripe, GitHub, and AWS all publish limits shaped this way.
- **Refill is lazy, not a timer.** No background job tops the bucket up. On each request the server computes `elapsed time × refill rate`, adds that many tokens (capped at capacity), and decides. The whole state per client is just a token count and a timestamp, so it scales to millions of API keys.
- **Fixed windows have a sharp edge.** A simpler limiter that counts "100 requests per minute" resets the count at the minute boundary, so a client can fire 100 requests at 11:59:59 and 100 more at 12:00:01 — double the intended rate in two seconds. Token buckets and sliding windows exist to close that gap.

## 🛠️ Tool of the Day

### GitHub Actions — CI/CD built into your repository

**GitHub Actions** is GitHub's built-in automation platform: define a workflow in a YAML file under `.github/workflows/`, and GitHub runs it for you on every push, pull request, release, or on a schedule. No separate CI server to set up.

```yaml
# .github/workflows/ci.yml
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run tests
        run: npm test
```

Why it is worth trying:

- **Zero setup for most projects.** Pick a starter workflow from the Actions tab and you have tests running in minutes — GitHub provides the runners.
- **A huge marketplace of reusable actions.** Checkout, language setup, caching, deployment, and security scanning are all one `uses:` line away, written by the community.
- **It automates more than CI.** Scheduled jobs, auto-labelling issues, publishing releases, and even this daily log repo's reminders are all workflows.

How to try it: in any repo, go to the **Actions** tab, choose a starter workflow for your language, commit it, and watch the first run go green.
